一、产品定位

✦ AI 微调（新增）

「基本满意，按我的要求改一点。」
基于当前内容做最小必要修改，能不改的不改，只执行用户明确要求，不改变产品事实。

↻ 重写（保留）

「不满意，重新生成一版。」
基于商品资料重新生成，允许句式/结构/语气/营销方式较大调整。

两者在 Prompt（独立 EDIT_SYSTEM）、Service（listing-edit.ts vs listing.ts）、UI（两个并列按钮）、计费（listing_ai_edit vs listing_rewrite） 上严格区分。AI 微调没有复用 Rewrite Prompt。

二、架构与数据流

1
【生成修改】POST /listings/[id]/ai-edit
认证→归属校验→组装 context（全部后端从 DB 取，不信任前端）→ estimate→reserve→AI Edit→后置 Fact/Platform 校验→consume→暂存 pendingEdit→返回 preview
2
【预览】前端展示 diff
原内容 vs AI 微调后 + 修改说明 + 事实冲突/平台规则/提示。未覆盖原 Listing。
3
【应用修改】POST /listings/[id]/apply-edit
从 DB 读 pendingEdit（前端只传 listingId，无法篡改 content）→ 旧 current 转 history → 创建新 version → 清空 pendingEdit
4
【取消修改】前端什么都不做
原 Listing 完全不变，不产生新 version。

三、数据库变更

model EcommerceListing {
  ...
  draft        Json     // 完整 Draft
  pendingEdit  Json?    // 新增：待应用的 AI 微调结果
                        // { field, instruction, content, changes, warnings, factConflicts, platformIssues, createdAt }
  ...
}

新增 EcommerceListing.pendingEdit（nullable Json）。设计目的：preview → apply 两步分离，apply 时后端从 DB 读 AI 已生成、已过 Fact 校验的内容，前端无法篡改 content 绕过校验。

四、API 设计

POST /api/ecommerce/listings/[id]/ai-edit

Request:  { "field": "title", "instruction": "突出便携性。", "idempotencyKey": "..." }
Response: { ok, preview: { field, original, content, changes[], warnings[], factConflicts[], platformIssues[] }, consumedCredits }
402:      { ok:false, code:"insufficient", error:"本次预计消耗约 X 额度，当前剩余 Y 额度", estimated, available }
409:      { ok:false, code:"duplicate", error:"该修改已在处理中或已完成" }
500:      { ok:false, error:"AI 修改失败，额度已退回，请稍后重试。" }

POST /api/ecommerce/listings/[id]/apply-edit

Request:  （无 body，后端从 DB 读 pendingEdit）
Response: { ok, listing: { id, version, status, draft, warnings, ... } }  // version+1

instruction 限长 1000 字符；field 白名单 5 个；context（productFacts/platform/market/language/platformRules）全部后端从 DB 取。

五、AI Edit Prompt（独立于 Rewrite）

Minimal Edit 原则（9 条硬性规则）：只改当前字段、只执行用户明确要求、能不改的不改、保留原结构/核心卖点、不改产品事实、不改目标市场/语言、禁止大幅重写、冲突时保持原事实并进 fact_conflicts、无必要修改时 content 返回原内容。

Structured Output（禁止 Markdown 解析）：

{ "content": "...", "changes": [{"type":"modified","description":"..."}], "warnings": [], "fact_conflicts": [], "platform_issues": [] }

六、Credit 生命周期

计费点
listing_ai_edit（新增 PricingRule：2 credits / 千字，按当前字段内容 + instruction 字符计量）
流程
estimate → reserve（原子检查余额，不足 402 直接阻止，不先执行 AI）→ AI Edit → consume / refund
幂等
reserve/consume 复用 CreditLedger 幂等键；route 层额外检查同 idempotencyKey 已完成 → 409 拒绝重复提交
失败
AI Provider 失败 → 自动 refund，提示「额度已退回」

七、Fact Validation 流程

双重防护：

① Prompt 约束：AI 输出 fact_conflicts，要求冲突时不执行修改、content 保持原内容。

② 后置兜底（本次实测后补强）：factConflicts 非空 → content 强制回退原内容 + changes 清空 + warnings 提示「已保持原内容不变，如需修改请先补充产品资料」。前端检测「微调后 == 原内容」时【应用修改】按钮显示「无需应用」并禁用。

实测：产品 facts 为 IPX4 Water-Resistant，用户要求「改成 fully waterproof」→ AI 返回 fact_conflict，content 保持 IPX4 Water-Resistant，未生成 waterproof。

八、Platform Validation

① Prompt 约束：把平台规则（maxLength 等）传入 prompt，要求优先遵守。

② 后置硬截断：长度超 maxLength 时确定性截断 + platform_issues 提示「已按平台字段长度限制（N 字符）调整内容」。

字段映射：title→title、bulletPoints→bullet_points、description→description、keywords→keywords（faqHighlights 无平台规则）。实测：要求「缩短到 150 字符」→ 结果 122 字符，满足限制。
