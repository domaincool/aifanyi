一、现状盘点：已经打好的地基

在动手接支付之前，先明确——记账能力已经完备，缺的只是「充值」这一条腿。现有 Credit 系统是这次商业化的最大资产：

  • Credit 引擎全生命周期：reserve / consume / release / refund / grant / expire / adminAdjust，34 单测全绿，含并发防超卖（行锁 + 应用层检查）。
  • 定价全配置化：PricingRule 表驱动 17 个 feature（文本/PDF/图片/字幕/文档/网页/润色/盲测/ASR/TTS/跨境电商 7 项），改价走表不改代码。
  • Grant 类型已预留商业化字段：PURCHASED（充值）、SUBSCRIPTION（订阅）、FREE_MONTHLY、BONUS、ADMIN_ADJUSTMENT、REFUND —— 数据模型层面已经把「钱怎么进账户」的类型定义好了。
  • 对账不变量：available + reserved == Σ Ledger.amount，天然支持与支付侧对账。
  • 获客与防滥用已就位：新用户注册送 300 额度；游客限流（60s/15 次 + 日预算 30 次/5000 字符/IP）；盲测免费引流。
结论：支付接入不是「从零建账」，而是「在已有的完整账本上补一个资金入口」。工程量比看起来小得多，风险主要集中在合规与收款主体，而不是技术。

二、变现缺口：为什么现在做

三个缺口，本质上是「有账没钱进」：

缺口现状影响
支付（充值）额度只能靠注册赠送，无购买入口有用户价值，无收入
定价（SKU）有内部 cost 规则，无面向用户的商品用户不知道「值多少钱、怎么买」
合规（主体/税务）无收款主体、无发票能力无法正规收款

关键优势：翻译边际成本极低（DeepSeek 单次约 0.0002 元），定价应走「价值定价」而非「成本加成」——毛利空间足够支撑免费额度拉新 + 订阅制锁客。

七、合规要点

  • 预付费（点数）定性：点数属「预付式消费」，需在用户协议中明示有效期、退款政策、余额处置（当前 Credit 已有 expire 机制，可直接复用并公示）。
  • 发票：接入个体户主体后可开电子发票；MoR 阶段（海外）由平台代开收据。
  • 数据与 PCI：卡号/支付密码绝不落地，只存订单号与第三方流水号，走第三方 H5/JSAPI 收银台。
  • 地区化定价：海外用户用美元档（$1/$5/$15），国内用人民币档，避免单一币种。
  • 退款风控：已消费额度不退款，未消费余额支持原路退（Refund 流程已备）。
