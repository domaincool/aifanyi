一、结论先行

可行，且成本很低。因为 6 个工具页背后的解析 + 翻译能力（PDF / 图片 OCR / 字幕 / Word-PPT / 网页 / 文本）已经全部上线，各自有独立 API。首页改造的本质是：加一个统一文件入口 + 按类型路由到既有 API + 复用结果区渲染，属于纯前端工作，不需要任何新的后端服务。

推荐方案：轻量内嵌版——首页给出「段落级双语对照」结果卡片 + 「打开完整工具」按钮，保留 PDF 阅读器等重交互在工具页完成，首页不膨胀。

二、目标体验

首页翻译框变成「万能翻译入口」，文本粘贴或拖文件进来都能翻译：

输入框→ 文本→文本翻译 API →结果卡片
📄 PDF→PDF API（进度轮询） →摘要对照 + 完整阅读器入口
🖼 图片→图片 API（OCR） →识别/译文对照
🎬 字幕→字幕 API（进度轮询） →双语字幕列表
📝 Word/PPT→文档 API →段落对照

三、交互设计（推荐：轻量内嵌版）

① 输入区改造

  • textarea 下方/右侧加「📎 文件」按钮 + 整框支持拖拽投放（拖 PDF/图片/字幕/文档进来自动识别）
  • 移动端：输入框下加一行小图标按钮（📄 🖼 🎬 📝），点击唤起文件选择
  • 上传时立即校验类型与大小（各类型上限见下表），错误就地提示

② 类型路由（前端判断，零后端改动）

用户输入识别方式路由到结果渲染
纯文本粘贴无文件POST /api/translate（现有）现有翻译结果卡片（不变）
PDF.pdfPOST /api/pdf/translate进度条 + 前 10 段对照 + 「完整阅读器」按钮
图片.png/.jpg/.webp/.gifPOST /api/image/translate图片缩略图 + 识别文字/译文两栏
字幕.srt/.vttPOST /api/subtitle/translate进度条 + 前 15 条对照 + 完整导出入口
Word/PPT.docx/.pptxPOST /api/doc/translate段落对照（含标题/列表标签）

③ 结果区策略

  • 首页统一「轻量结果卡片」：原文/译文段落对照 + 复制 + 「打开完整工具 →」按钮
  • 重交互（PDF 双栏阅读器、字幕导出 SRT、Word 下载）留在各工具页，首页只做「能看、能复制、能跳转」
  • PDF / 字幕走 taskId 轮询（现有 API 已支持），图片 / 文档为单次请求直接返回

四、两种方案对比

方案 A：轻量内嵌版（推荐）推荐

首页结果区为统一对照卡片，重功能跳转工具页。

  • ✅ 开发量小（~2h），首页保持轻快
  • ✅ 5 类文件全部覆盖，转化闭环（首页 → 工具页）
  • ✅ 与现有 6 个工具页零冲突
  • ⚠️ PDF/字幕结果在首页是「摘要级」，完整功能要跳转

方案 B：全功能内嵌版备选

把 PDF 阅读器、字幕导出等完整组件搬进首页结果区。

  • ✅ 首页即完整工作台，不跳转
  • ⚠️ 首页 JS/视觉重量明显增加（PDF 阅读器 ~30KB+）
  • ⚠️ 与工具页功能重复，维护双份
  • ⚠️ 开发量 ~1 天，移动端适配压力大

六、实施步骤（方案 A 落地拆解）

步骤内容工作量

4移动端按钮行适配 + 深浅色主题样式~20min

七、风险与注意点

  • 额度共享：PDF / 字幕每日 5 文件是 IP+UA 计数，首页入口与工具页共享同一额度（不新增），需在 UI 明确提示剩余额度
  • 同步接口耗时：图片 / 文档单次请求 10-30s，需清晰的 loading 状态与超时兜底
  • 首页重量：只引入类型路由逻辑（<5KB），不引入 PDF 阅读器等重组件（方案 A 已规避）
  • 多文件批量：本轮只做「单文件」，一次拖多个文件提示「每次一个」；批量上传可作为二期

八、二期可选扩展

  • 批量文件队列（多 PDF / 多字幕依次翻译）
  • 「识别语言自动选目标语言」智能默认
  • 文件历史（登录用户可在账户中心查看最近翻译文件）
  • 直接粘贴图片（Clipboard API 从剪贴板拖图翻译）
