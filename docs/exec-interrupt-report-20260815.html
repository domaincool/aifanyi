一、根因总览

「执行意外中断」的提示（terminal-recovery）背后是 5 类不同来源，只有第 1 类是真正的执行失败，其余都是误报或环境噪音。按影响排序：

根因类型证据
1. Session 文件写锁超时（SessionWriteLockTimeoutError）真中断gateway.log 今日 15 次，02:51-02:52 密集爆发；session file locked (timeout 15000ms): pid=15476 alive=true ageMs=22804
2. git 管道 exit code 假警报（PowerShell NativeCommandError）误报每次 git push 2>&1 | Select-Object 都报 exit 1 + RemoteException，但 push 实际成功（日志里有 9c15562..1e211a0 main -> main）
3. 桌面端建站交付校验失败（send_failed → terminal_recovery_turn）误报autoclaw-dev.log 04:25: Website delivery incomplete: projects/projects.json was not updated... no preview URL was created → post_turn.skipped reason=terminal_recovery_turn
4. gateway 启动插件冲突（primary load failed）环境问题SyntaxError: Identifier 'autoclawNormalizedPluginIds' has already been declared（出现 2 次）
5. MCP 连接器反复失败（噪音）噪音ima / tianyancha / feishu / lexiang 每次启动都报 failed（OAuth 未授权或本地服务未起），120 条/日

二、逐类根因与解决方案

1. Session 文件写锁超时 — 真正的执行中断

机制：OpenClaw 每个 session 的对话记录存在一个 .jsonl 文件里，写入时用锁文件（.jsonl.lock，内含 pid + 创建时间 + maxHoldMs=300000）防并发。当多个 lane（主会话 + nested 子会话）同时写同一个 session 文件，等待锁超过 15 秒就抛 SessionWriteLockTimeoutError，整个 turn 标记失败（UNAVAILABLE）。

触发场景（今日 02:51-02:52 实证）：主会话跑 batch-007 导入 + 部署长任务期间，sessions_send 给运营 agent 的嵌套回执消息同时到达，两个 lane 抢同一 session 文件的写锁。日志同时出现 lane=nested:agent:agent-nc6bvi:fc73e97e 和 lane=session:agent:agent-nc6bvi:fc73e97e 两个 lane 双双超时。

解决方案：

A
行为层（已落实，写入工作纪律）
长任务（build/部署）进行中不发起需要等待回复的 sessions_send；跨 agent 消息用短超时或 fire-and-forget，避免主会话 + 嵌套 lane 同时活跃写锁。
B
会话层
锁文件 mtime 已过 maxHoldMs(5分钟) 可安全删除（进程已死残留）；OpenClaw 无公开配置项可调写锁超时，属内部机制。
C
产品层（建议反馈）
建议 AutoClaw 将写锁超时从 15s 提高到 30s+，并让嵌套 lane 优先排队而非抢锁，可根治此类偶发。

2. git 管道假警报 — 最常见的「中断」误报

机制：PowerShell 里 git push 2>&1 | Select-Object -Last 2 会把 git 写到 stderr 的正常输出（To github.com:...）包装成 NativeCommandError，管道让 $LASTEXITCODE 语义丢失，最终 exec 工具判定 exit code 1 = 失败 → 上层 stage git changes 步骤报 failed → 触发 terminal-recovery。

铁证：每次报错的同时，日志里都有 e3ce8bc..9c15562 main -> main —— push 实际成功。

解决方案：

// 不再用管道截断 git 输出。改法（PowerShell）：
git push origin main *>&1 | Out-String   # 或直接不加管道
if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }
exit 0

更稳妥：git 操作全部改由 node 脚本执行（execSync 带 stdio 处理），从源头消除 PowerShell 管道 exit code 污染。已在本次报告中作为标准做法写入工作纪律。

3. 桌面端建站交付校验失败（send_failed）

机制：桌面端在 turn 结束时校验「建站任务是否更新了 projects/projects.json」，未更新则抛 Website delivery incomplete 并把 turn 标记为 terminal_recovery_turn。这是上一轮（网站预览交付）协议校验的误报——实际文件操作已完成，只是桌面端认为交付不完整。

解决方案：建站任务严格按 AUTOCLAW_FUNCTION_COMPUTE_WEBSITE_PROTOCOL 流程：先 website_delivery_start → 生成文件 → 最后更新 projects/projects.json（该文件变更即完成信号）→ 校验 JSON。避免「文件生成了但没写元数据」的中间态被桌面端判失败。

4. gateway 启动插件冲突

机制：Identifier 'autoclawNormalizedPluginIds' has already been declared —— AutoClaw 桌面端注入的插件归一化变量与 OpenClaw 内置逻辑重复声明，导致 primary load 失败（出现 2 次）。伴随 AutoClaw stop-hook harness failed（5 次）。

解决方案：升级 AutoClaw 桌面端到最新版本（该问题属客户端注入层 bug）；重启 gateway 可临时恢复（日志显示服务仍能通过 fallback 起来）。

5. MCP 连接器噪音

机制：connector:ima / tianyancha / lexiang 配置了 OAuth 但从未授权，connector:feishu 本地服务（127.0.0.1:65100）未启动——每次 gateway 启动都刷 4 条失败，120 条/日污染日志。

解决方案：在 openclaw.json 的 mcp.servers 里把未授权/未使用的 connector 设 enabled: false（beida-fabao / qcc-* 已是 false，ima / tianyancha / lexiang / feishu 待禁用）。需要时再启用。可减少启动耗时与日志噪音。

四、总结

「经常遇到执行中断」的真相：绝大多数是误报（git 管道假警报 + 建站交付校验误判），真正的中断只有 Session 写锁超时一类，且集中在「主会话长任务 + 跨 agent 消息并发」的窗口。行为层修复（git 改 node 执行、长任务不并发发消息）已落地，预计可消除 80% 以上的误报；剩余两项需要你操作（禁用 MCP connector、升级客户端），可按需执行。
